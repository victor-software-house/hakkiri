# Prose linter decisions

- 2026-11-09 The linter is a ctl CLI with its own rule and config format, built from the best prior art: Vale's prose checks (word lists, swaps, counts, metrics), ast-grep's structural scoping (`inside`, `has`, `not` over the document tree), and flat-config files and levels in `.ctl/<verb>.yaml`. Upstream Vale styles are converted when prose-style builds. Field names are not settled. (operator, 2026-11-09)
- 2026-11-09 The format must be as clear, ergonomic, efficient and powerful as the best tools in the field, building on them rather than on Vale's syntax. (operator, 2026-11-09)
- 2026-11-09 Release 1 reaches parity with Vale and ProseStyle v0.0.7 on Markdown, MDX and Rust comments, proven by the prose-style cases and an alert diff over real repositories, and also ships rate rules (a habit counted per sentence or per N words) with the frequency-habit rules in ProseStyle. Intended differences from Vale: Rust block comments are linted, string literals are not read, no panics. (operator, 2026-11-09)
- 2026-11-09 Each programming language gets a profile that knows where its prose lives and in what syntax: rustdoc Markdown, TSDoc and JSDoc tags, Go doc, Python docstrings, plain comments. Rules can target doc text, plain comments or tags. Release 1 ships Rust, TypeScript and JavaScript, Markdown and MDX; more languages follow as profiles on tree-sitter grammars. Human-language profiles are not in scope. (operator, 2026-11-09)
- 2026-11-09 Rules ship as versioned packages. prose-style stays its own repository and publishes a package per tag; a project pins it by version and hash in `.ctl/<verb>.yaml`, and the linter fetches and caches it with no separate sync step. Rules and engine release on their own schedules. (operator, 2026-11-09)
- 2026-11-09 Release 1 is the CLI, run from the `lint:prose` mise task, CI and a lefthook pre-commit on staged files. The engine keeps a per-file API, and a language server with alerts and quick fixes is release 2. (operator, 2026-11-09)
- 2026-11-09 The CLI is named `hakkiri` (はっきり, "clearly, plainly"), with no `ctl` in the name; its config is `.ctl/hakkiri.yaml`. (operator, 2026-11-09)
- 2026-11-09 No Vale issue about parallel file arguments; hakkiri replaces Vale in our projects. (operator, 2026-11-09)
- 2026-11-09 hakkiri is rendered from the templates repository, plans each slice as an OpenSpec change, and tracks its work in a qctl `tasks.yaml`. (operator, 2026-11-09)
- 2026-11-09 Rules are structural first: a rule selects nodes in the document tree, and a pattern only narrows what the structure already selected. (operator, 2026-11-09)
